# zcode-tps 0.5.1 × ZCode 3.11.2 兼容性评估与修复方案

日期：2026-09-13  
评估对象：本地 `main`（`32b0633`，zcode-tps 0.5.1）与本机 ZCode 3.11.2.6792

## 1. 结论摘要

zcode-tps 的核心统计链路健康：主请求筛选、错误及取消请求排除、标题请求排除、token 总量、轮次聚合、缓存命中率、子代理归因和只读查询均未发现破坏性缺陷。现有自动化测试全部通过，真实数据库上的查询耗时也远低于 hook 的 8 秒宿主超时。

但是，当前 0.5.1 不宜原样发布。发布前应优先解决以下问题：

1. 会话级 Decode 与请求级 Decode 使用了不同的最小解码窗口，造成统计契约不一致。
2. 0.5.1 的 p90 算法在小样本下明显偏低，需要明确并统一分位数定义。
3. 默认速率行中的 `Decode` 实际是整个会话的历史加权值，标签没有表达时间范围，并可能混合不同模型。
4. 根 README、插件 README、manifest 描述和 hook 注释已与 0.5.1 的实际行为漂移。
5. ZCode 3.11.2 数据库已经出现新的内部请求来源，当前插件会静默忽略；应在完整报表中单列并对未知来源告警。

建议先完成正确性和发布资料修复，再决定默认速率行是否用 TTFT 取代 Decode。暂不需要修改 ZCode 数据库索引、引入增量缓存或增加第二套 compact 模式。

### 2.3 真实数据库观察

评估期间数据库仍被运行中的 ZCode 持续写入，因此以下数字是动态快照，不应当作长期固定值：

- 同一批 469 条子代理的 `parent_user_message_id` 全部不能与主请求的同字段匹配。

- 按输入规模十分位观察，输入中位数从约 49k 增至约 231k 时，TTFT 中位数大致维持在 8–9 秒；输入达到约 300k 以上后，TTFT 中位数升至约 12.4–12.6 秒。
- 输出不足 200 token 的有效请求，端到端速率中位数约 11.6 tok/s；输出至少 200 token 的请求中位数约 28.4 tok/s。短请求速率确实更容易受固定延迟影响。
- 独立 Node 进程执行真实查询 7 次，耗时平均约 163 ms，范围约 126–263 ms；该测量包含 Node 启动，仍远低于 8 秒 hook 超时。

## 3. 对原六项优化建议的复核

### 3.1 子代理用量被整体排除

**原发现正确，但当前版本已经修复。**

0.1.8 起插件通过共享 `trace_id` 将派生子代理归入主会话，当前实库验证表明该关联是完整且无歧义的。`parent_user_message_id` 在当前 ZCode 3.11.2 数据中不具备所设想的主子请求关联关系，不应改用。

当前仍需改善的是展示层：包含子代理时，完整 `session` 统计已经并入子代理，但默认行的 token 和缓存仍取 `usage` 的主对话范围，只用 `(主)` 后缀提示。建议改成明确的 `主对话 N tok`，完整 `/tps` 再分别展示主对话、子代理和合计。

相关实现：

- `plugins/zcode-tps/scripts/token-rate.mjs` 中的子代理 trace 归因。
- `session` 为含可归因子代理口径；`usage` 保持基础主对话口径。

### 3.2 TTFT 增加上下文规模

**有实际信息价值，但不能表述成单一因果解释。**

当前代码已经在可选 `ttft` 段中输出 `首字 Xs · ctx Y`。真实数据只显示弱到中等相关，且 TTFT 同时受模型、服务负载、缓存、调度和网络影响。因此合适的解释是“上下文规模是首字延迟的一个重要背景变量”，而不是“首字慢就是上下文大”。

建议文案改成更自然且与 token 口径一致的形式：

```text
首字 12.5s（读 302k）
```

它比 `ctx 302k` 更容易与“输入包含缓存读取、并不等于本轮新消费”这一事实对应。

### 3.3 “上轮 tok”措辞易误读

**判断正确，已经完成。**

当前代码使用：

```text
最近轮 读 244k（出 2.4k）
```

该文案比“上轮 244k tok”准确，避免把重复读取的上下文误解为新生成量或直接计费量。无需回退。

### 3.4 “最近”速率抖动大

**现象正确，但不建议把短请求替换成上一有效值。**

回退旧值会让展示值失去“最近”的真实性，并引入额外状态和过期语义。0.5.0 已将默认端到端指标从最近单请求改为最近轮加权均值，这比静默沿用旧值更稳妥。

如果还要减少误解，可在 `/tps` 中同时展示最近轮的有效请求数和输出量，或者在样本输出很短时明确标注“短输出，速率波动大”，但不能替换真实值。

### 3.5 速率行的复述开销

**成本客观存在，但 0.5.0 已经完成主要优化。**

当前默认行已经压缩为四段：

```text
⚡ 最近轮均 23.7 tok/s · Decode 38.8 tok/s · 会话 7.66M tok · 缓存 91.1%
```

无需再增加第二套 compact 模式。配置系统已经允许用户通过 `rateLineFields` 自行减少字段。继续增加模式会扩大文档、测试和兼容性成本，节省的 token 很有限。

注入规则本身仍有固定上下文开销，且自动行依赖模型遵循指令。除非 ZCode 将来提供原生状态栏或结构化 UI 插槽，否则这一成本无法从插件层彻底消除。

### 3.6 查询性能

**暂不需要优化。**

当前查询耗时健康，而且 ZCode 3.11.2 已经为 `query_source`、`trace_id` 和会话/轮次建立索引。插件应继续只读访问，不应修改 ZCode 自身数据库结构。

后续只需监控：

- hook 真实耗时是否持续接近宿主超时；
- 是否出现 SQLite 锁竞争；
- 数据库达到十万至百万行后查询耗时是否发生量级变化。

在出现新证据前，不引入增量缓存，不创建额外索引。

## 4. 当前待修缺陷

### 4.1 会话 Decode 的最小窗口与请求级不一致

当前请求级 Decode 和 `decodeStats` 都要求：

```text
dec_ms >= 200
```

但会话级主请求和子代理 Decode 聚合只要求：

```text
dec_ms > 0
```

这导致 1–199ms 的极短解码窗口会进入会话 Decode，却不会进入请求级 Decode 和分布统计。真实库中已经观察到 5 条此类请求。

**修复方案：**

- 主请求会话 Decode 改为 `dec_ms >= DECODE_MIN_MS`。
- 子代理会话 Decode 同样改为 `dec_ms >= DECODE_MIN_MS`。
- 统一注释、README、命令说明和样本数定义。
- 增加 1ms、199ms、200ms 三个边界测试。

**验收标准：**请求级、分布、主会话、子代理会话的 Decode 有效样本集合采用同一个最小窗口常量。

### 4.2 p90 算法对小样本明显偏低

当前索引计算为：

```js
Math.floor(frac * (n - 1))
```

例如样本 `[100, 181.8, 500]` 的 p90 会返回 `181.8`。这不符合常见 nearest-rank 定义，并且对 `/tps` 的少量样本很不直观。

**推荐方案：nearest-rank**

```text
index = ceil(p × n) - 1
```

理由：

- 无需将全量样本载入 JavaScript。
- SQL 的 `ORDER BY ... LIMIT 1 OFFSET ?` 结构可以继续使用。
- 小样本含义直观，3 个样本的 p90 为最大值。
- 容易在 README 中准确说明。

如果更重视连续统计，也可以选择线性插值，但实现、查询和解释都会更复杂，不符合当前轻量插件定位。

**验收标准：**

- 明确记录采用 nearest-rank。
- 覆盖 1、2、3、10 个样本的 median/p90 测试。
- 测试不要锁定一个未说明统计定义的“近似值”。

### 4.3 默认 Decode 标签掩盖统计范围

默认行中的 `Decode X tok/s` 实际是：

- 整个数据库留存会话范围；
- 以输出量除以解码窗口总和得到的加权值；
- 默认可包含子代理；
- 可能跨时段、跨拥堵状态和跨模型。

因此它不能自然地与左侧“最近轮均”并列理解为同一时间范围。

**最低限度修复：**改成 `Decode会话均 X tok/s`。

**推荐产品方案：**默认行改为：

```text
⚡ 最近轮均 X tok/s · 首字 Ys（读 Z） · 主对话 N tok · 缓存 H%
```

把 Decode 放回 `/tps`，并按模型展示或至少明确会话范围。这样默认行集中解释当前体感，完整报表负责诊断吞吐。

### 4.4 “可与官方 Decode 直接对比”表述过强

本地公式 `output / (duration - TTFT)` 是合理的纯生成速度近似，但官方公开资料没有给出足够严格的采样协议，无法保证模型范围、并发、请求长度、计时边界和统计方法完全相同。

**修复方案：**统一改成：

> 近似纯生成 Decode 口径，可用于同环境趋势观察；不同服务、模型、请求长度和官方测速结果不保证可直接等价比较。

### 4.5 新内部请求来源被静默忽略

当前精确筛选 `main_turn` 和 `subagent` 能保护核心速率不被标题、压缩或验证请求污染，这是正确行为。但插件没有向用户说明其他真实模型用量的存在。

**修复方案：**

- JSON 增加 `auxiliary`，按 `query_source` 返回 completed 请求数、输入、输出和总量。
- `/tps` 单列“辅助/内部请求用量”。
- `session_title`、`goal_summary_title` 默认归为标题类。
- `compact`、`target_completion_verification` 默认归为系统辅助类。
- 未识别的非空 `query_source` 加入 `warnings`，但不影响退出码，也不自动进入主统计。
- 默认速率行不显示辅助来源。

这样既保持用户体感指标纯净，又能及时发现 ZCode 升级带来的来源变化。

### 4.6 发布资料漂移

已确认：

- 根 `README.md` 仍写当前版本 0.4.2，并展示旧默认速率行。
- `plugins/zcode-tps/README.md` 标题仍写 0.5.0。
- `marketplace.json` 和插件 manifest 描述声称每轮默认显示 TTFT、本轮 token，实际默认四段并不包含二者。
- `prompt-submit.mjs` 注释仍写默认三段、`all` 六段，实际为默认四段、`all` 七段。

**修复方案：**

- 所有版本文字统一到即将发布的版本。
- 根 README 示例改为当前默认行。
- manifest 只描述确定存在的能力，不把可选字段写成默认行为。
- 增加发布测试，至少检查 README 顶部版本、默认示例关键字段和 hook 注释所对应的常量，避免再次漂移。

## 5. 建议实施顺序

### 阶段 A：发布阻断修复

1. Decode 主会话和子代理统一采用 `DECODE_MIN_MS`。
2. p90 改为 nearest-rank，并补齐小样本测试。
3. 将“与官方直接对比”改为有限度、可验证的描述。
4. 若 Decode 暂时继续留在默认行，先改名为 `Decode会话均`。
5. 修复所有版本、示例、manifest 描述和代码注释漂移。
6. 运行全部测试、`git diff --check` 和一次真实只读查询。

### 阶段 B：默认行决策

推荐默认字段：

```json
["rates", "ttft", "session", "cache"]
```

推荐渲染：

```text
⚡ 最近轮均 23.7 tok/s · 首字 12.5s（读 302k） · 主对话 7.66M tok · 缓存 91.1%
```

需要同时确认：

- TTFT 缺失时直接省略该段，不制造估算值。
- `first_token_at - started_at` 若用于回退，应在 JSON 中暴露来源，例如 `ttftSource: "derived"`，避免直接值和推导值不可区分。
- 含子代理时，默认行明确写“主对话”，不再使用含混的 `会话 ... (主)`。

### 阶段 C：完整报表增强

1. 增加 `auxiliary` 请求来源统计。
2. 对未知 `query_source` 告警。
3. Decode 按 `model_id` 分组，避免多模型会话混算后只给一个数。
4. `/tps` 同时展示主对话、子代理、辅助请求和可解释的总计。

### 阶段 D：发布

1. 确认 `package.json`、`marketplace.json`、`.zcode-plugin/plugin.json` 与 README 版本一致。
2. 确认 changelog 完整描述口径变化。
3. 确认安装缓存中的插件版本与目标发布版本一致。
4. 推送前再次执行 `git fetch --all --prune` 并核对目标远端。
5. 推送 `main`，确认 GitHub `origin/main` 已包含预期提交。
6. 在 ZCode 插件管理页验证更新提示、安装版本和运行结果。

## 6. 必须补充的测试

### Decode 边界

- `dec_ms = 1`：不参与任何 Decode 指标。
- `dec_ms = 199`：不参与任何 Decode 指标。
- `dec_ms = 200`：参与请求、分布、主会话和子代理 Decode。
- TTFT 直接值缺失但时间戳可推导时，验证回退及来源。
- TTFT 和时间戳都缺失时，只进入端到端与用量统计。

### 分位数

- 单样本：median 与 p90 都等于该样本。
- 两样本：验证 nearest-rank 边界。
- 三样本：`[100, 181.8, 500]` 的 p90 应为 `500`。
- 十样本：验证 p50/p90 的精确索引。
- 子代理不进入基础 `decodeStats`，除非未来显式新增含子代理分布字段。

### 来源和模型

- 已知辅助来源正确进入 `auxiliary`。
- 未知来源只产生 warning，不污染 headline。
- 两模型会话按模型分别统计 Decode。
- 子代理模型与主模型不同的合成用例不得被静默混成无标签单值。

### 发布一致性

- 三处机器版本字段完全一致。
- README 顶部版本与机器版本一致。
- 默认速率行示例与 `DEFAULT_RATE_FIELDS` 一致。
- `RATE_SEGMENTS`、配置文档和 hook 注释中的字段数量一致。

## 7. 暂不实施

- 不使用 `parent_user_message_id` 替代 `trace_id`。
- 不用上一条有效速率覆盖当前短请求速率。
- 不增加第二套 compact 模式。
- 不修改 ZCode 数据库索引。
- 不将标题、压缩、验证请求混入主对话端到端速率。
- 不引入全量历史缓存或增量账本，除非真实规模和锁竞争产生新的性能证据。

## 8. 完成定义

本轮修复可以在满足以下条件后视为完成：

1. 请求级、分布和会话级 Decode 的有效样本条件完全一致。
2. p90 定义明确、实现正确，并覆盖小样本测试。
3. 默认行中每个指标的时间范围和统计范围不会被误读。
4. 新的 ZCode 内部请求来源可见但不污染核心指标。
5. 文档、manifest、示例和实际默认配置一致。
6. 全部自动化测试通过，真实只读查询无错误，hook 耗时保持在安全范围。
7. 本地 `main`、目标 marketplace 和 `origin/main` 的预期提交与版本完全一致。
