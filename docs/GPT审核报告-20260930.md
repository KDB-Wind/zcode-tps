## 3. 缓存百分比与 token 聚合专项

设请求输入为 I、缓存读为 C、输出为 O、reasoning 为 R。已确认 C 是 I 的子集；源码将 R 作为 O 的明细，见 `token-rate.mjs:188–190`。

正确公式应为：

```text
总 token = ΣI + ΣO
缓存命中率 = 100 × ΣC / ΣI
非缓存读输入 = ΣI − ΣC（只有字段有效、关系成立时才可派生）
```

不能使用 `I + C + O`，也不能把百分比分母改为 `I + C`。该百分比是输入 token 的命中占比，不是命中请求数占比，也不是价格折扣或费用节省比例。

### 3.1 逐项核对

| 对象 | 实现 | 裁定与位置 |
| --- | --- | --- |
| 最近轮总量 | `t_i + t_o` | 正确，`token-rate.mjs:419` |
| 最近轮缓存命中 | `t_cr / t_i`，保留一位小数 | 正确，`:424` |
| 主对话 usage 总量 | `i + o` | 正确，`:435–440` |
| 默认行缓存命中 | `usage.cacheRead / usage.input` | 正确，`:443–445、528–531` |
| 含子代理 session 总量 | 分别累加主 / 子输入与输出，再相加 | 正确，`:385–388、449` |
| 含子代理 session 缓存命中 | `totalCacheRead / totalInput` | 正确，`:450` |
| auxiliary 总量 | 各组 `i + o`，组间相加 | 正确，`:299–313` |
| cacheCreation / reasoning | 独立明细字段，没有额外加进上述 total | 无双计，`:414–440` |

缓存读与输入的原始累加位于 `token-rate.mjs:232–247、340–341`；没有以“未缓存输入”为分母，也没有对缓存百分比取请求级算术均值。

合成验证 `I=1000、C=900、O=100、R=40`：turn / usage / session 总量均为 1100，缓存命中均为 90%，行输出 `会话 1.1k tok · 缓存 90%`。已有 `degrade.test.mjs:78–82、99–108` 及 `correctness.test.mjs:265–283` 分别验证普通比例、0%、100% 和零输入。

**无需改缓存公式，也无需仅因本次怀疑而勘误历史速率行。** 只有发现历史数据库字段语义与当前已确认语义不同、具体错误输入或统计范围被误标时，才应定向勘误。

### 3.2 正确公式之外的限制

- 默认行 `会话 N tok` 和 `缓存 H%` 取主对话 usage，而 Decode 可含子代理；存在归因子代理时加 `(主)`，见 `token-rate.mjs:523–531`。这是明确的产品范围划分，不是漏加缓存。
- cacheCreation 的包含关系没有在本次用户数据事实中明确；不能推导未缓存输入的细分或精确计费。本报告只确认当前没有再次相加它，且契约明确 total 为 input + output。
- 对非法负 token、`cacheRead > input`、文本字段或计数缺失，当前缺少系统性质量校验；正确公式也不能保证异常输入结果可信。建议告警并暴露未知量，不以简单钳制到 0–100% 隐藏异常，见 F10。
- 累计来自库内留存 completed 请求，可随宿主清理下降；输入可能多次读取同一上下文。不能解释成唯一上下文大小、全历史账本或实际费用，见 `plugins/zcode-tps/README.md:68–71`。

## 4. 速率、时间窗与轮次边界专项

### 4.1 精确定义

```text
dur = duration_ms ?? (completed_at − started_at)
ttft = time_to_first_token_ms ?? (first_token_at − started_at)
dec = dur − ttft

V = completed、output > 0、500ms ≤ dur < 3600000ms（默认值）
D = V 且 dec ≥ 200ms

最近轮均 = 1000 × Σ当前观察轮 V 的 output / Σ同批 V 的 dur
会话端到端均 = 1000 × Σ留存会话 V 的 output / Σ同批 V 的 dur
Decode 会话均 = 1000 × Σ留存会话 D 的 output / Σ同批 D 的 dec
```

公式中 1000 把毫秒转为秒，最终保留一位小数。参数读取见 `runtime.mjs:71–83`，时长与 TTFT 表达式见 `token-rate.mjs:29–34、173`，有效性与聚合见 `:189–205、215–258、392–403`。当前 D 尚缺有效数值和非负 TTFT 校验，见 F07 / F10；以上描述是实际逻辑，不是宣称其已完整防御异常输入。

**最近轮均**只取当前 session 的 completed main_turn。轮 ID 来自按完成时间倒序的第一条主请求，即 `histRows[0].turn_id`，不是最近有效请求 `latest` 的 turn ID（`:180、219–225`）。同轮的全部留存主请求进入 token / 请求数聚合，仅 V 子集进入速度分子与分母（`:242–258、414–423`）。因此零输出请求计用量，但不拉低均速的分母。

**Decode 会话均**覆盖当前会话全部留存有效主请求，默认再加 completed、query_source=subagent、trace 匹配的请求（`:329–358、398–403`）。不是最近轮 Decode，也不是固定最近 60 请求、最近一天或滑动时间窗。可混合不同模型和时段，应作为会话服务速率趋势解释。

**decodeStats**只覆盖主对话，mean 是请求级速率算术均值，median / p90 是 nearest-rank；与会话 Decode 的时间加权均值不同（`:265–279`；`release.test.mjs:378–393、424–433`）。含子代理时其样本数也可以比 `session.decodeSamples` 少，属于范围不同，不是统一窗口修复失效。

### 4.2 分组是否漏算或重算

正常非空字符串 ID 下，主聚合先限定 session，再按 turn_id 匹配，故不同会话同名 turn 不会混在一起。SQL IN 使用 distinct trace 集合，不是把每条子代理与每条主请求多对多 JOIN；同一 trace 有多个主请求也不会重复放大单条 subagent（`token-rate.mjs:165、174、242–258、329–337`）。

本次设置 `TOKEN_RATE_HIST=1`，A 会话同轮两请求、B 会话同名轮一请求：history=1，A 最近轮 requests=2、output=200、duration=2000ms、avgTps=100；A session output=200。证明普通轮次聚合没有因 history 截断而漏算，也没有跨会话重算。已有 `release.test.mjs:135–141` 还覆盖最近有效请求被 60 条无效行压出 history 后的深查询。

以下边界需区分缺陷与设计：

| 边界 | 当前行为与判断 | 证据 |
| --- | --- | --- |
| NULL / 空字符串 turn_id | turn 未知；存在未知 ID 时 usage.turns=null，保留 knownTurns 和用量；正确 | `token-rate.mjs:171、234、410、432–447`；`release.test.mjs:113–123` |
| 仅含空白 turn_id | 错认已知轮次，可能虚假合并；缺陷 F09 | `token-rate.mjs:171` |
| 最新轮只有零输出请求 | turn 仍指向新轮、avg=null；latest 可指向旧有效请求；按明确规则降级为会话均，标签随之变化 | `release.test.mjs:182–189`；`token-rate.mjs:501–505` |
| 相同 completed_at 的不同轮 | 没有稳定第二排序键，最新观察轮选取欠确定；兼容性风险，未证明生产出现 | `token-rate.mjs:180、222` |
| 较旧轮迟到请求最后完成 | 按“最近完成请求所属轮”选择，可能选择较早开始的轮；不是按用户轮开始顺序 | `token-rate.mjs:219、406–407` |
| 同一 trace 对应多个主会话 | 每个会话各自可归因同批子代理，跨会话合计可能重叠；当前归因假设未校验唯一性 | `token-rate.mjs:329–337`；历史实库无歧义仅见 `docs/ZCODE-3.11.2-COMPATIBILITY-AND-REPAIR-PLAN.md:63` |
| error / cancelled / 未完成请求 | 被 completed 筛选排除；符合现有范围，不能称为全部尝试消耗 | `token-rate.mjs:174、294、336` |
| 重复行 / 重试尝试 | 每个满足筛选的物理行都参与；不是按 logical_request_id 去重；目前无法判定实库是否有重复记账 | `token-rate.mjs:232–250、340–347` |

并发请求的 duration 是求和，工具执行与请求间隔没有进分母，所以“最近轮均反映现在的端到端体感速度”只能作有限解释。两条并行 100 tok / 1 秒请求返回 100 tok/s 的加权服务速率，整轮墙钟吞吐则可能为 200 tok/s。源码和命令文档已经明确这种区别，见 `commands/tps.md:47`；无需因并行时长相加而判定重算。

TTFT 只是从请求起点到宿主记录的首 token 事件，不保证等于用户首次看到正文的时间；output 包含 reasoning 时也不能将 Decode 一概理解成可见正文速度。应继续采用“近似纯生成口径”，不要对标官方数字等价性。

## 5. 已确认缺陷与修复建议

优先级：P1=发布前应优先修复的功能失败 / 诊断失真；P2=条件触发的统计边界和可靠性缺陷。优先级不表示生产发生频率。下列合成复现证明实现有缺陷，不表示已确认真实库含这些异常数据。

### F01 — P1：强制索引选择不排除部分索引

**证据：** `token-rate.mjs:87–99` 仅检查首列与覆盖评分，没有检查 `PRAGMA index_list` 的 partial；`:168` 将同一强制索引用于 main 与 auxiliary（`:293–295`）。

合成库加入 `(session_id,query_source,status,completed_at) WHERE query_source='main_turn'` 的部分索引后，`query('A')` 抛 `no query solution`。该索引能覆盖主请求，却不能覆盖 auxiliary 的排除主请求条件，即使 auxiliary 实际为空也会失败。

**建议：** 优先只选普通非部分索引；索引不可用时最多一次取消强制索引的回退并提示 warning。使用专门的 SQL 标识符引用函数替代 JSON 字符串转义；保留普通生产索引的性能收益。SQLite 的 INDEXED BY 是强制要求而非提示，不能使用就会准备失败。[SQLite INDEXED BY](https://www.sqlite.org/lang_indexedby.html)、[部分索引条件](https://www.sqlite.org/partialindex.html)。

**验收：** 无索引、普通索引、仅部分索引、普通与更高评分部分索引并存、特殊字符索引名；结果与不强制索引路径一致。只有查询路径修改后重跑相关性能矩阵。

### F02 — P1：默认关闭的 Stop 掩盖 prompt 错误

**证据：** `stop.mjs:77–84` 在检查开关前 startHealth，再写 disabled；`runtime.mjs:57–59、156–177` 按 session 而非 hook 分文件，更新合并旧记录；`doctor.mjs:192` 将新鲜 disabled 判为正常。

本次实际子进程：prompt 因缺库记录 `error / unable to open database file`；执行默认关闭的 Stop 后，变为 `disabled / error=null`，doctor 最近采集 `ok=true`。这在不启用通知的默认配置下也会损害诊断。

**建议：** 健康记录按 session + hook 类型隔离；Stop 关闭时尽早退出，或只更新自己的状态；prompt 也明确写 hook 类型，避免继承旧 `hook:'stop'`（`prompt-submit.mjs:12` 未设置）。doctor 分别展示注入与通知链路。

**验收：** prompt 错误不被关闭的 Stop 消除；同会话不同 hook 及交错完成互不覆盖。当前 runId 保护只能防部分迟到终态，不能替代按 hook 隔离。

### F03 — P1：Stop 异常路径不记录终态和原因

**证据：** `stop.mjs:77–78、103–105`；异常 catch 直接退出，没有 complete(error)。与 `prompt-submit.mjs:46–48` 的正确错误记录路径不同。

本次缺库探针：退出码 0、stdout 空，但健康记录 `running / error=null`。持续独占锁探针同样如此，见第 6 节。doctor 只能提示中断 / 超时，不能还原真正的数据库失败。

**建议：** catch 接收异常，记录 error、耗时和确定终态，再以 0 静默放行。水位写失败、配置损坏、缺 SQLite、缺列及查询失败都应有原因。健康写入本身失败仍允许放行，但不能声称已记录成功。

**验收：** 每条可捕获失败都有 error 终态；宿主强制终止才保留 running，由 doctor 解释为未完成。

### F04 — P1：macOS 通知代码错误转义字符串边界

**证据：** `stop.mjs:62–64` 对 JSON.stringify 结果的全部双引号加反斜杠，包括本应作为 AppleScript 字符串边界的引号；`:69` 使用无 shell 的 spawn，不能指望 shell 消除转义。

提取当前 sendNotify 并替换 spawn 后，捕获到 `osascript -e` 参数的字符串边界前含反斜杠；普通文本也被构造成 `display notification \"audit test\" ...`。Apple 示例使用正常字符串字面量。这是代码构造缺陷；**未在 macOS 执行，具体错误码与桌面表现未验证。** [Apple 通知脚本说明](https://developer.apple.com/library/archive/documentation/LanguagesUtilities/Conceptual/MacAutomationScriptingGuide/DisplayNotifications.html)。

**建议：** 固定 AppleScript handler，将文本经 argv 传入；或正确区分字符串内部转义和边界引号。不要使用 JSON 转义替代目标语言规则。

**验收：** 命令构造单测加 macOS 实际脚本执行；中文、emoji、引号、反斜杠和换行。可见弹窗还需要有桌面与通知权限的环境确认。

### F05 — P1：未提交通知就标为已展示 / 成功

**证据：** `stop.mjs:98–102` 先写水位、记录 ok，再 sendNotify；`:39、69–72` 的 suppress / spawn error / catch 均不反馈提交结果，也没有退出状态记录。

因此平台命令缺失或执行失败时，下次相同水位会被 `:92–96` 跳过。测试 suppress 直接不发送，也会留下相同“成功”状态；它不是通知成功证据。静默放行能保护宿主，但当前同时丢失了诊断与重试机会。

**建议：** 区分 query 成功、通知待提交、已提交和失败；明确失败允许有界重试。必要时用短生命周期发送子进程反馈结果，避免常驻服务。状态只承诺命令提交，不能保证用户看到了横幅。保留客户端及系统通知权限边界，不把强制开启权限作为可靠性修复；当前首通知注册表行为位于 `stop.mjs:45–50、102`。

**验收：** 命令不存在、非零退出、提交成功、超时、权限拒绝与并发调用。实际显示与提交成功分开记载。

### F06 — P2：单槽水位与主请求时间不足以完成可靠去重

**证据：** `runtime.mjs:44–45` 是全局单文件；`stop.mjs:86–99` 只保存 / 比较一组 sessionId + shownAt；水位源为主请求 `token-rate.mjs:451–453`，而 Decode 范围可含子代理（`:398–403`）。

- A 主请求不变，加入同 trace 子代理：Decode 111.1→555.6 tok/s，session.total 1100→3000，coverage 水位仍为 1001000；再次 Stop 时水位文件完全不变，变化被拦截。

同毫秒新增、旧时间补写、原行 token 回填和未来时间戳占据最大值也能形成类似风险，但未逐项实测。同会话并发 Stop 的读 / 比较 / 写不构成原子占用，存在重复提交风险，尚未并发复现。

**建议：** 按 session 哈希存独立去重状态，明确通知是“每宿主轮一次”还是“统计变化一次”；覆盖实际展示范围的稳定指纹，必要时配可靠宿主 turn ID；排除 sampledAt 等每次变化字段。不要只哈希四舍五入的文本。对同时提交加轻量原子占用，并定义失败重试规则。

**验收：** A→B→A、不变快照、子代理完成、同时间新增、旧数据补写、同会话并发和失败重试。不要把“恰好一次可见通知”作为无法兑现的承诺。

### F07 — P2：TTFT 缺少类型与物理范围校验

**证据：** `token-rate.mjs:32、173、192–205、215–216` 只校验 dec 最小窗口，没有保证 TTFT 为数值且非负；该表达式亦用于子代理 `:335`。

本次复现：

**建议：** 统一解析和校验有效 TTFT：数值有限、`0 ≤ ttft ≤ dur`，并继续要求 dec≥200ms。显式值异常时是否改用时间戳推导需明确策略；推导值同样校验，记录来源和降级原因。e2e 与用量不应因单独 TTFT 坏值全部丢失。

**建议：** 校验 Date 的 getTime，非法时间返回 null，并附 warning；保持原始值可诊断。最近轮排序、coverage 和去重对非法 / 未来时间的处理另行明确，不把不可表示日期与合理范围内未来日期混为一类。

**验收：** Date 范围内外、边界、NULL / TEXT；一条坏日期不拖垮全报表。`release.test.mjs:320–323` 目前仅测普通日期和字符串，未测此范围。

### F09 — P2：空白 turn_id 形成虚构轮次

**证据：** `token-rate.mjs:171` 仅 `NULLIF(turn_id,'')`，未采用 `runtime.mjs:7–10` 的共享有效 ID 规则。

**建议：** 用 validIdSql 判定有效文本 ID，非法值投影为 NULL；合法 ID 保留原值，不 trim 后强行合并不同 ID。

**验收：** 空串、NULL、ASCII / Unicode 空白、非文本 ID、合法但带前后空格 ID；未知轮次不推测，累计照常保留。

### F10 — P2：token 字段类型校验不足导致 JS 与 SQL 样本不一致

**证据：** `token-rate.mjs:182–189` 的 JS 比较与 `:215、236–250` 的 SQL 比较没有统一数值类型守卫；用量 SUM 与 `?? 0` 也不能证明异常字段是合法计数。

**建议：** SQL 与 JS 统一合法非负数值 token 和有效正时长定义；异常值不计速率但保留请求计数与数据质量信息。对用量未知值暴露异常数 / 完整性，不悄悄补零当作准确账本。与 F07 合用一套数值校验规则，避免两端再漂移。

**验收：** 文本、负数、NULL、超大值、缓存读超输入；history / turn / session / subagent / decodeStats 有效样本一致。是否允许非整数 token 也应先声明契约。

## 6. Stop 机制、库锁与测试降级覆盖

### 6.1 当前 turn-end 到底是什么

Stop 当前只发送系统通知，stdout 正常为空，不输出 block / additionalContext，也不触发模型续跑（`stop.mjs:2–10、92–105`）。真正的对话末尾引用仍由 UserPromptSubmit 的 additionalContext 与显示指令驱动（`prompt-submit.mjs:19–25、39–44`），因此默认仍滞后一轮、且依赖模型遵循指令。

`turnEndLine` 默认 off，只有 true / notify / toast 等支持值开启，见 `runtime.mjs:48–54`。不应把“Stop 立即通知”写成“即时插入当前回复末尾”。此前续跑会折叠答案的方案已明确废弃，0.6.0 不应恢复它。

### 6.2 库锁、空数据与时限

查询采用 readOnly DatabaseSync，busy_timeout=2000ms，整个 query BUSY / LOCKED 最多重试一次，间隔150ms；有单事务快照，见 `token-rate.mjs:73–81、113–145、454–458`。这是合理的短锁保护；不能把两次 timeout 简单等同于完整 hook 必定只等待4.15秒，打开连接、SQLite 内部及其他阶段仍有耗时。

本次实际 Stop 子进程 + 临时 DELETE 日志库 BEGIN EXCLUSIVE：**约6613ms，退出0，stdout空，health仍为running，error=null**。这证明本场景可在8秒前放行，也确认 F03；不证明所有规模 / 冷启动 / 输入延迟下都能守住8秒。宿主超时设置见 `hooks/hooks.json:29、44`。仓库既有锁结果约6274.7ms，测量边界见 `docs/PERFORMANCE.md:21、42–46`；它不是本次重测百万行结论。

完整 schema 的空表：本次 Stop 退出0、无输出、无新水位，符合 `stop.mjs:90–96`。表不存在 / 缺必需列则是query失败；Stop静默放行，但诊断存在 F03。空数据与不兼容库必须继续区分，不能用空白输出概括为“全部成功降级”。

Stop读stdin没有长度或时间限制，并在EOF之后才读配置与记录running（`stop.mjs:15–24、75–82`）。本次保持stdin开启500ms，即使配置off，进程仍未退出。**这是受控输入下可复现的等待行为；没有证据表明当前ZCode正常调用真的不关闭stdin。** 建议默认off快速退出、输入限长 / 限时，并将启动、输入、查询及状态写入纳入总预算。同步SQLite不能只靠同线程setTimeout中断，只有实测需要时再引入短查询子进程。

### 6.4 本体升级与hook协议风险

当前Stop识别stdin `session_id`，再回退ZCODE_SESSION_ID / CLAUDE_SESSION_ID；prompt只读环境变量而不解析stdin（`stop.mjs:76`；`prompt-submit.mjs:10`）。若宿主未来把session仅放stdin，prompt可能回退到全局last-session / 最新主会话，造成窗口归属风险。**本次未发现也未验证实际协议已经变化。**

损坏或非对象stdin被Stop吞成{}，BOM不经parseJson处理（`stop.mjs:20–24`），不一定导致停用，也可能用env或自动识别；应对输入来源和异常作有限诊断。测试常显式提供env与session_id，不能代表未来宿主全部组合。

“Stop拿到刚结束整轮完整数据”是待验证契约。`stop.mjs:4`和根`README.md:36`作此断言，但query只保证已落库completed快照，而且turn.completion仍为unknown（`token-rate.mjs:406–413`）。若最终usage在Stop之后才提交，当前没有短时重采样。建议先记录当前宿主版本、事件输入、usage提交与Stop顺序的只读验收，再决定是否补有界等待；无证据时不要盲目轮询。

## 7. 升级路线与0.6.0特性取舍

### 7.1 推荐先做0.5.5：可信度补丁

保持正常输入下JSON字段、默认四段行和只读数据库契约，优先完成F01–F05，再合并F06–F10的相关最小修复。这是修复已存在的功能，不应等workflow分账设计成熟后才处理默认诊断失真。

### 7.4 本轮不建议做

继续不写宿主数据库、不创建索引、不做全历史增量账本、后台daemon或通用遥测平台：现有百万行优化已有收益记录，当前没有新规模证据要求增加缓存一致性成本（`docs/PERFORMANCE.md:15–23、35–46`）。

### 10.2 最值得借鉴：收尾时采样，但必须说明它是部分数据

上游0.8.3当前主要展示路径是：

1. UserPromptSubmit写提问时间，并注入收尾统计指令。
2. 已经使用过工具的回答，在最终总结之前再执行一次`node token-rate.mjs --turn --current`。
3. 模型引用这次命令返回的行；旧的prompt时采样只作为禁止展示的内部背景。

依据上游`hooks/prompt-submit.mjs:32–41、64–65`。这与本项目当前“发送消息时采样并引用该行”不同，也与已弃用的Stop block续跑不同：它利用正常回答收尾阶段主动采样，不依赖Stop来触发第二次回答。

**对你的价值：** 新会话第一条消息就是长任务且已调用工具时，能在最终总结前显示当前任务已落库请求的统计，缓解默认注入滞后一轮的空窗。这个方向值得作为0.6.0可选能力评估。

**必须保留的边界：** 采样之后还会生成最终总结，采样值不包含那部分产出；纯问答无既有工具调用时，上游故意不为统计单独调用工具。上游README `:125–131`明确解释这个限制，但`:115`又用“完整的本问数据”，措辞并不完全一致。正确展示应是“本问已落库部分 / 总结前采样”，而不是“本轮最终完整用量”。[上游README固定版本](https://github.com/shy3130/zcode-tps-monitor/blob/60c0e19f0d096b94c5a64647e33515767bedbf69/README.md#L105-L131)。

采样脚本本身不调用模型API，但收尾加一次工具操作会增加工具执行、上下文与随后模型处理开销；因此不能简单继承本项目“零额外模型调用”宣传。究竟多产生多少请求 / token依赖宿主，需实际A/B验证，不在本次猜测。

上游更新记录`CHANGELOG.md:6–8`声称其客户端不触发Stop；本项目9/19材料描述Stop可触发但不block的systemMessage不显示。两者宿主版本、配置与观测条件未在本次对齐，不能用上游说法直接推翻本项目旧证据，更不能把systemMessage当作已恢复的原生显示通道。

| 版本与发布 | 仍为0.5.5一次发布，包含0.5.3优化与0.5.4最终能力 | 新增功能不继续复用旧版本号；发布建议第8节不变 |

0.5.5默认四段行和prompt时采样保持；不在修复补丁里悄悄把所有回答改为收尾工具采样。理由是展示时间、统计窗口、额外工具操作和依赖模型遵循指令的方式都发生变化，应作为用户可选择的新能力交付。

### 10.6 修订后的0.6.0计划：可选收尾采样 + 可解释分账

保留第7.2节的workflow / retry / TTFT / turn_usage取舍，新增可选收尾采样候选。建议按下面顺序实现；这不是已确定的配置API或已完成实现。

**A. 先构建安全的“本问快照”契约。**

- 将已有last-session活动时间与本问记录分开；按session保存`promptStartedAt`、唯一prompt标识，以及宿主确实提供时的turnId。SessionStart / Stop不改写提问时间。
- CLI带明确session与本问标识，返回结构化状态：有效部分数据、尚无数据、归属未知、查询失败；不要把这些都变成无法区分的空字符串。人类可读自动行可以在无有效数据时省略。
- 已验证的宿主turnId是首选；没有可靠ID时，开始时间、已有请求ID集合等只提供排除 / 辅助证据。`completed_at ≥ promptStartedAt`不够；生成一个本地nonce也不能单独证明数据库行属于该nonce。
- 使用时间推导时先验证宿主写入与时钟语义，暴露归属依据 / 信心；证据不足时不标签为本问，自动显示跳过。不能为了避免空行拿最新旧轮充数。
- 选轮和聚合仍限定当前session completed main_turn，复用现有只读事务；不把完整同轮所有行加载到JS后再求和，也不改写e2e / Decode公式。
- 返回sampledAt、completion=unknown、采样阶段及明确缺失范围；如需首段TTFT，依据可靠请求开始顺序选取，不能简单把最早完成行当作首个开始的请求。

**B. 在已有工具任务的最终总结前，允许一次收尾采样。**

建议新增默认关闭的独立配置，例如`wrapUpSample:false`（名称仅为提案）。开启时，SessionStart与prompt只注入一种一致的展示规则；历史prompt行可作为不展示背景，但优先减少无必要背景token。只对已使用工具的任务采样一次，查询失败或无数据时正常完成回答，不再为统计触发模型续跑 / 循环。

现有turnEndLine系统通知可独立保留。若与收尾采样同时开，要说明一个是总结前部分快照、一个是Stop时已落库快照；即便数值不同也可能合理，不应共享一个水位把更完整采样静默吃掉。始终尊重客户端工具及通知权限，无法执行时省略统计，不影响任务结果。

示例文案方向：

```text
本问已落库部分：端到端均 X tok/s · 主请求 N 次 · 输出 O tok · 采样 HH:mm:ss
```

“最近轮均”仍用于现有历史快照；两者不可只换标签而保持错误归属。最终总结后才完成的请求可以在下一次/tps或实际Stop采样中看到，不能在总结前预估补账。

**C. 再完成可靠的消耗分账。**

收尾采样解决“什么时候可看到”，dwf / error / retry解决“算了哪些请求”，两者独立。workflow归属仍必须按第7节验证真实键，互斥分类 / ID集合防重；TTFT增强现有字段，不误名HTTP TTFB；turn_usage只对账。可以分阶段预发布，不必在0.6.0首个候选里一次塞满所有方向。

如果宿主不能提供足够的本问归属证据，0.6.0可先只交付分账与诊断；收尾采样延后。不要把上游的时间比较包装为“强保证”来降低这个门槛。

### 10.7 新能力的必要验证与收益判定

| 行为 | 必须验证的结果 |
| --- | --- |
| 无状态、坏状态、BOM、过期 / 未来时间、session不符 | 不把旧轮当本问；有明确reason |
| 上一轮迟到完成 / 重试，辅助或错误请求更晚，未知turn | 主轮选择和归属不被劫持；无证据跳过 |
| 多窗口同session、同时prompt、Stop / SessionStart写状态 | 提问边界不被覆盖，旧标识不选择新问数据；明确同session并发的支持边界 |
| 普通单轮长工具任务、纯问答、最终总结继续生成 | 前者可显示部分快照；纯问答不强行加工具；不宣称已含最终总结 |
| 收尾采样启用 / 关闭，通知同时启用 / 关闭，权限拒绝 | 开关作用一致，无统计驱动循环，任务照常结束 |
| output含reasoning、first-token缺失、零输出和异常字段 | 复用0.5.5有效性规则，用量不随速率缺失消失 |
| 真实宿主A/B | 记录调用次数、总token差、采样延迟、漏附率、错归属率、回答是否折叠；结果支持收益后才考虑改变默认 |

最轻实现仍是共享query + 小型CLI入口 + 一致hook指令 + 合成fixture / 宿主冒烟脚本，不需要独立agent来完成采样。已有测试通过且本轮没有源码改动，因此没有重复跑本地npm test；上游完整测试套件本次未执行，审阅其断言后用更针对性的隔离反例复核。
