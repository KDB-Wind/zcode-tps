# 查询基准

运行：`npm run benchmark`。仅使用脚本新建的临时 SQLite 数据库，完成后删除；不会访问或修改 ZCode 的真实数据库。

## 2026-09-07 本地测量

环境为 Windows、Node 24.14.0；10 万条 completed 请求，20 个主会话，每个主会话归因后 5,000 条请求，含 20% 子代理请求。每种索引条件预热一次，再采样 7 次。

| 条件 | 中位耗时 | 样本 P95 |
|---|---:|---:|
| 合成库无索引 | 134.7 ms | 145.6 ms |
| 合成库有会话及 trace 测试索引 | 38.8 ms | 45.1 ms |

持续独占锁场景：查询最终返回 `database is locked`，实测耗时 6,556.5 ms。该数值接近 hook 的 8 秒宿主超时，需要在真实客户端环境中继续观察；不能仅凭 2 秒 busy timeout 推导整次 hook 的耗时上界。

测试索引为 `(session_id, status, query_source, completed_at)` 和 `(trace_id, status, query_source)`。这些仅用于对比实验，不是对真实数据库的修改建议。结果说明索引布局会影响查询成本，目前没有证据要求引入增量缓存。

## 测量边界

- 包含每次 query 的只读连接、schema 检查、统计和关闭连接。
- 不包含 Node 进程启动、hook 状态文件 IO、模型调用和 ZCode 的界面开销。
- P95 来自 7 个热样本，不是生产流量分布的可靠估计；扩大样本后再做容量判断。
- CPU、磁盘缓存、数据库结构和请求分布均会影响结果。这里没有宣称 ZCode 实际延迟达到上述数值。

下一步优先在真实宿主中采集 hook 耗时和锁竞争频率，再决定是否调整查询或缓存策略。
