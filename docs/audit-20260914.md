# zcode-tps v0.5.2 全量文件审计(2026-09-14)

审计人:zcode-tps v0.5.3 审计优化轮。范围:**100% 逐文件**(非抽查),清单见附录 A。
方法:逐行审读 + 真实库只读探查(PRAGMA/COUNT,无任何写操作)+ 现有 66 个测试用例对照。
分级:P0=崩溃/错数/注入;P1=大库性能/契约缺口,本轮必修;P2=防御性/可观测性,本轮尽量修;P3=记录不动。

## 0. 结论速览

- **P0:0 个。** SQL 全参数化,无注入面;hook 全路径输出严格 JSON;统计口径与冻结契约一致。
- **P1:3 个。** 单次查询 ~14-16 条 SELECT 重复扫描(大库线性劣化)、基准 fixture 索引与真实库不符、NULL/空白 query_source 请求全统计静默不可见。
- **P2:4 个。** doctor 时间戳 TEXT 时 "NaN 分钟前"、model_usage 表不存在时错误文案误导、benchmark 无内存/冷启动/真实分布(T2 交付)、空白 turn_id 计为已知轮次(口径不一致,择机)。
- 缓存失效:插件**无任何文件级缓存**(每次 query 全新只读连接),不存在 mtime/大小失效问题;T2 亦不引入缓存(维持 0.4.2 冻结决策)。

## 1. SQL 注入面(任务项 1)

**结论:安全。** 所有含外部输入的查询均为 `?` 参数化:

- 会话 ID:`token-rate.mjs:105` 显式 sid 必须过 `validId`(runtime.mjs:7),`token-rate.mjs:139/151/186/198/206/214/222/226/246/288/294/301/359` 全部绑定参数。
- SQL 片段拼接仅限常量与硬编码列名:`DURATION_SQL`(token-rate.mjs:29)、`DECODE_SQL`(:32)、`DECODE_MIN_MS`(:34,常量 200)、`validIdSql(col)`(runtime.mjs:10,仅以字面量列名调用:token-rate.mjs:59/64/242/277/281)。
- `HIST/MIN/MAX` 来自 `querySettings`(runtime.mjs:57-70),强校验后仍以参数绑定(token-rate.mjs:151/186/206)。
- 未知来源不进 SQL 文本(auxiliary 分组走 GROUP BY 结果,token-rate.mjs:247-263);警告消息只进 JSON 字符串。

## 2. Schema 变更兼容(任务项 2)

**结论:契约完备,两处文案/可见性缺陷。**

- 必需列(runtime.mjs:13-17)完整覆盖 `base` SELECT 的无条件引用列(token-rate.mjs:142-145);可选列(turn_id/cache_creation/trace_id)均先 `schema.columns.has` 再引用(:142-143、:271、:369、:390)。缺必需列→整查询失败→hook 空注入(PLAN-0.4.0 §3.7 冻结边界,degrade 用例 27 覆盖)。
- ZCode 升级新增 query_source:0.5.2 已按来源分组 + 未识别告警(token-rate.mjs:233-263)。真实库 3.11.2 六种来源与 AUX_CLASS 吻合(实测:compact/goal_summary_title/session_title/target_completion_verification/main_turn/subagent)。
- **P1-3:NULL/空白 query_source 的 completed 请求在所有统计中静默不可见。** 主统计限定 `query_source = 'main_turn'`(:145);辅助查询又以 `validIdSql("query_source")` 把 NULL/空白排除(:242)。若 ZCode 升级后某来源写入 NULL,相关请求从主统计、auxiliary、告警三处同时消失,违背 0.5.2 "来源变化必须可见" 的设计意图(CHANGELOG 0.5.2)。证据:`plugins/zcode-tps/scripts/token-rate.mjs:145,241-244`。
- **P2-2:model_usage 表整个不存在时,错误文案误导为"缺少列"。** `PRAGMA table_info` 返回空集 → `schema.missing` 为全部必需列 → 报 "model_usage 缺少列: …"(token-rate.mjs:124;runtime.mjs:23-27)。doctor 已区分(doctor.mjs:62-63),query 路径未区分。

## 3. 缓存失效(任务项 3)

**结论:不适用。** 插件无任何持久缓存层:每次 `query()` 经 `openDb()`(token-rate.mjs:74-81)新建只读连接、`BEGIN` 单事务快照(:122)、`finally db.close()`(:408-410)。无 mtime/大小指纹,无失效风险。0.4.2 已明确 deferred 项(不引入增量缓存),本轮维持。唯一"缓存"是进程内 `zoneFormatterCache`(runtime.mjs:97-108),按 tz+格式为键,无失效需求。

## 6. 性能(任务项 6;P1-1/P1-2 详见 §8)

**P1-1:单次 query() 最多 ~14-16 条 SELECT,每条独立重扫 model_usage。** 显式 sid + includeSubagents + 有解码样本时:

1. histRows(:151) 2. latestRow(:186) 3. sumRow(:191) 4. aggrRow(:201) 5. decodeRow(:209) 6. dcRow(:220) 7. pick median(:225) 8. pick p90(:225) 9. auxRows(:239) 10. traceList+subAggr(:283) 11. traceList+subDecodeRow(:289) 12. traceList+subSum(:296) 13. turn 轮聚合(:352);自动识别再加 resolveAutoSid 两条(:59,:64)。

T0 基线:10 万行合成库 no_indexes 中位 352.2ms;真实库 0.7 万行实测约 163ms(3.11.2 评估文档 §2.3)。行数线性外推 100 万行 ≈ 3.5s+,叠加锁等待(4.2s)可逼近/突破 8s hook 宿主超时——属于任务定义的 "全表扫描线性劣化" P0/P1 级性能问题。
真实库已有索引(只读探查):`model_usage_query_source_idx(query_source)`、`model_usage_trace_idx(trace_id)`、`model_usage_session_turn_idx(session_id,turn_id)`、`model_usage_started_model_idx(started_at,provider_id,model_id)`;无 completed_at 索引,ORDER BY completed_at 走排序。

**P1-2:benchmark 的 fixture 索引与真实库不符。** `test/benchmark.mjs:55-56` 建 `(session_id,status,query_source,completed_at)` 与 `(trace_id,status,query_source)`,比真实索引覆盖面强(含 status/query_source/completed_at),因此 "fixture_indexes" 场景系统性低估真实单查询成本、高估索引收益。修复:新增镜像真实索引场景,保留旧场景对照。

**修复方案(行为不变):** 条件聚合合并 —— sumRow+aggrRow+decodeRow+turn 四合一;sub 三合一;decodeStats 材化 CTE 三合一;resolveAutoSid 优先级排序二合一;latest 优先从 histRows 派生(仅当最近 HIST 条全无效才深查询)。目标:每次 query 的 SELECT 数 ≤ 8,并以"语句计数"测试先红后绿。

### T2 追加发现与修复(矩阵第一轮暴露)

- **生产索引形同虚设**:真实库索引 `(session_id,turn_id)` 不含 status/query_source,SQLite 无 ANALYZE 统计时规划器弃用之而全表扫描(1M 行 real 场景 2.3-3.5s ≈ 无索引)。修复:只读探测 session_id 首列索引(按覆盖打分选优)并对会话等值语句 `INDEXED BY` 固定路径 → typical 21× 提升。
- **锁路径回归**:mmap/页缓存 pragma 在独占锁下各付一个完整 busy 等待周期,锁场景 6.5s→12.8s(>8s hook 预算)。修复:pragma 移至 schema 首次成功读取之后 → 6.3s。此发现验证了"pragma 也有锁成本"这一非显然约束。
